# Развёртывание: GitHub Pages + два Google-аккаунта

## 1. GitHub Pages

В репозитории `KUPRYAKOFF/practicus` откройте Settings → Pages → Build and deployment → Source → **GitHub Actions**. Затем Actions → **Check and publish GitHub Pages** → Run workflow для `main`, если предыдущий запуск не опубликовался.

Workflow запускает тесты, проверку синтаксиса, сборку, сохраняет artifact `apps-script` и публикует только `dist/site`. Ни `server/`, ни Script Properties не выдаются сайтом Pages. Исходники сервера находятся в публичном репозитории, поэтому секретов в них быть не должно.

Пока `web/config.js` содержит `apiUrl: ""`, доступна только демонстрация. Это ожидаемое начальное состояние.

## 2. Основной аккаунт: Apps Script и Sheets

Войдите в основной аккаунт, откройте `https://script.google.com/`, создайте отдельный проект Practicus. Доступ редактора предоставляйте только доверенным администраторам: редактор Apps Script потенциально имеет доступ к Script Properties.

Получите готовые файлы из artifact `apps-script` последнего успешного workflow или выполните локально `npm ci && npm run build`. В проекте Apps Script должны оказаться:

```text
appsscript.json
Main.gs
Core.gs
Bridge.html
```

Для `clasp`:

```sh
cp .clasp.json.example .clasp.json
# Укажите scriptId своего проекта в локальном .clasp.json
npx @google/clasp login
npx @google/clasp push
```

`rootDir` должен указывать на `dist/apps-script`. `.clasp.json` не коммитится. Для локальной работы с clasp включите Google Apps Script API в пользовательских настройках Apps Script.

## 3. Отдельный аккаунт: OAuth Drive

Почему не достаточно расшарить папку: файл в личном Drive обычно принадлежит создателю, а его квота может расходоваться в основном аккаунте. Сервер должен обращаться к Drive от имени второго аккаунта. Создавать отдельный Apps Script на втором аккаунте не требуется.

Бесплатный вариант использует OAuth-клиент Google Cloud и scope `https://www.googleapis.com/auth/drive.file`. Сервер получает доступ только к файлам, созданным этим приложением. Billing для этой схемы включать не нужно.

1. В Google Cloud Console создайте проект, включите Google Drive API.
2. В Google Auth Platform настройте OAuth consent screen. Для обычных аккаунтов это External. Добавьте второй аккаунт как тестового пользователя на время проверки.
3. Создайте OAuth Client ID типа **Desktop app**, скачайте JSON **за пределы репозитория**. Не загружайте его в чат или GitHub.
4. На своём компьютере с Node 20.19+ выполните:

```sh
node scripts/authorize-drive.mjs /абсолютный/путь/client_secret.json
```

5. Откройте выведенный URL на том же компьютере. В Google обязательно выберите **аккаунт хранилища**.
6. Локальный помощник создаст закрытую папку `Practicus_Private_Storage` от его имени и покажет на локальной странице четыре свойства. Скопируйте их в Project Settings → Script Properties основного проекта Apps Script:

| Свойство | Значение |
|---|---|
| `DRIVE_CLIENT_ID` | OAuth client ID |
| `DRIVE_CLIENT_SECRET` | Client secret |
| `DRIVE_REFRESH_TOKEN` | Постоянный серверный refresh token |
| `DRIVE_ROOT_ID` | ID только что созданной закрытой папки |

Помощник хранит значения в памяти и не выводит секреты в терминал или файлы. После ответа локальный сервер закрывается. Если авторизация прервана, завершите процесс и повторите. Порт `127.0.0.1:8765` должен быть свободен.

Для длительной эксплуатации проверьте публикационный статус OAuth-приложения: для External в режиме Testing Google обычно ограничивает срок refresh token семью днями для таких scopes. Переведите приложение в Production по правилам Google и повторно выдайте согласие при необходимости. `drive.file` относится к ограниченному доступу приложения; требования Google Console всё равно нужно проверить в своём проекте. Истечение/отзыв токена означает необходимость повторного подключения.

Не делайте папку публичной и не предоставляйте студентам доступ к ней. Скрипт «Проверить Drive» проверяет владельца папки и отсутствие публичных/domain-разрешений. Прямые Drive ID никогда не выдаются обычному клиенту.

## 4. Остальные Script Properties и запуск

| Свойство | Значение |
|---|---|
| `AUTH_SECRET` | Минимум 32 случайных байта в base64; не человекочитаемый пароль |
| `PAGES_ORIGIN` | `https://kupryakoff.github.io` — без пути `/practicus` и без завершающего `/` |
| `INIT_ADMIN_LOGIN` | Ваш первый логин администратора |
| `INIT_ADMIN_PASSWORD` | Первый временный пароль, 10–128 символов |
| `DB_ID` | Оставить отсутствующим: `setup_` создаст отдельную закрытую книгу в основном аккаунте. Или ID заранее созданной закрытой таблицы |
| `FILE_LIMIT_BYTES` | Необязательно; по умолчанию 26214400, можно уменьшить |
| `FILE_TRANSPORT_VERIFIED` | `false` до завершения испытаний |

Сгенерировать `AUTH_SECRET` на своём компьютере:

```sh
node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"
```

Запустите в редакторе Apps Script функцию `setup_` и предоставьте разрешения основного аккаунта. Она создаст листы, первого администратора, удалит временный пароль из Script Properties и установит ежечасный триггер очистки. Повторный запуск не сбрасывает данные. Авторизацию Drive выполняет отдельный refresh token, а не OAuth-токен Apps Script.

Не меняйте `AUTH_SECRET` без причины. При его компрометации смените его и отзовите все сессии. Потеря секретов Drive требует нового подключения, а не публикации папки.

## 5. Публикация Web App и подключение интерфейса

Deploy → New deployment → Web app:

- Execute as: **Me** (основной аккаунт).
- Who has access: **Anyone / Все**, включая пользователей без Google-входа.

Если политика вашего Google-аккаунта запрещает анонимные Web Apps, этот транспорт не пройдёт проверку: не заменяйте собственную авторизацию публичным Drive. Это ограничение нужно выяснить на этапе прототипа.

Скопируйте production URL вида `https://script.google.com/macros/s/DEPLOYMENT_ID/exec` и измените **только** публичный адрес:

```js
window.PRACTICUS_CONFIG = Object.freeze({
  apiUrl: 'https://script.google.com/macros/s/DEPLOYMENT_ID/exec',
  name: 'Practicus',
});
```

Сделайте коммит `web/config.js`, дождитесь Pages. `/dev` не подходит. При изменении серверного кода нужно выполнить сборку, push в Apps Script и Deploy → Manage deployments → Edit → **New version**, сохранив URL. Изменение одних Script Properties не требует новой версии кода.

При первом входе смените временный пароль. Откройте Настройки → Проверить Drive, убедитесь, что отображается второй аккаунт. Создайте группу, преподавателя, студента, назначьте доступ преподавателю. Пройдите испытания в отдельной тестовой таблице/папке, затем настройте рабочие ресурсы.

## 6. Импорт из Sheets

Администратор может создавать пользователей через интерфейс. Дополнительно поддерживается `UserIntake`:

1. Не меняйте заголовки. В новой строке заполните обычным текстом `full_name`, `login`, `role` (`student`, `teacher`, `admin`), `group_id` (ID или точное название группы), `subgroup` (`1`/`2` для студента). `id`, `status`, `error` оставьте пустыми.
2. В кабинете администратора на странице Пользователи нажмите «Импорт из Sheets».
3. Обрабатывается до 10 строк за запрос. Сохраните однократно показанные временные пароли. Исправьте строки со статусом `error`, если они есть.
4. После обработки данные хранятся в каноническом JSON-формате ячеек. Пользователь не создаётся повторно для строки `done`.

Если ответ с временным паролем потерян, используйте сброс пароля через интерфейс. Восстановить уже выданный открытый пароль нельзя.

## 7. Очистка и резервное восстановление

`housekeeping_` запускается раз в час. Старые файлы недоступны сразу после смены поколения; физическое удаление выполняется очередью очистки. В одной итерации удаляется до 50 файлов, ошибки повторяются. При большом хвосте запустите функцию вручную несколько раз. Не удаляйте строки файлов или резервы вручную — они нужны для восстановления и поиска сирот по `appProperties`.

До обновления схемы сделайте закрытую копию книги метаданных средствами Sheets. Не публикуйте её. В этой версии автоматические резервные копии бинарных файлов не создаются: это исключает скрытое сохранение удалённых работ и расход дополнительной квоты. Для восстановления метаданных укажите ID проверенной закрытой копии в `DB_ID`, отзовите старые сессии, запустите диагностику на тестовом окружении и сверьте текущие поколения с наличием файлов Drive. Копия метаданных не восстановит уже удалённые файлы.

Регулярное резервирование и автоматизированная сверка физического Drive с копией БД требуют отдельной эксплуатационной проверки. Не включайте такую копию в двухлетний срок файлов без явно заданной политики удаления копий.
