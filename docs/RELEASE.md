# Выпуск Practicus 1.0.0

Владелец подтвердил работу приложения и исключил проверки загрузок. Приёмка файлов и нагрузка 30 пользователей не являются условиями этого выпуска и не заявляются как пройденные. Новые автоматические проверки относятся к коду, резервированию, восстановлению и согласованности версий.

## Обновление уже работающего приложения

1. Скачайте архив **practicus-apps-script-v1.0.0.zip** из GitHub Release v1.0.0. Для ручного копирования используйте папку apps-script именно тега v1.0.0, а не изменяющийся main.
2. В существующем проекте Google Apps Script выделенного аккаунта замените Main.gs, Core.gs, Bridge.html и appsscript.json. Сохраните существующие DB_ID, DRIVE_ROOT_ID, AUTH_SECRET и пользователей. Не создавайте новую базу вместо рабочей.
3. В Script Properties задайте **FILE_UPLOADS_ENABLED=true**. Это переключатель приёма файлов, не отметка о прохождении испытаний. Старый FILE_TRANSPORT_VERIFIED поддерживается только как запасной вариант при отсутствии нового свойства; его можно удалить после перехода.
4. В списке функций выберите **runInitialSetup** → «Выполнить». Повторный запуск сохранит существующую базу и создаст папку резервирования, ежедневный триггер и первую резервную копию. Разрешения подтверждаются выделенным аккаунтом. Если операция завершилась ошибкой, исправьте её и повторите, не сбрасывая ID.
5. Deploy → Manage deployments → Edit → **New version**. Execute as — выделенный аккаунт, доступ — Anyone. Сохраните прежний URL /exec: интерфейс уже использует его.
6. В GitHub → Actions → **Verify and release Practicus** → Run workflow выберите Workflow from **main**, release_ref **v1.0.0**, deploy **true**. Workflow проверит сборку и публичный номер/отпечаток Apps Script, затем обновит Pages. Никаких файловых или нагрузочных испытаний он не выполняет.
7. В интерфейсе администратора откройте Настройки. Проверьте версию 1.0.0 и время первой резервной копии. На странице https://kupryakoff.github.io/practicus/release.json доступны публичные сведения о выпущенном интерфейсе.

Если Apps Script ещё старый, публикация Pages завершится отказом до обновления сайта. Работающая версия сайта сохранится. Обновите сервер по шагам 2–5 и повторите workflow.

## Что теперь происходит автоматически

- Push в main и pull request запускают тесты, проверку синтаксиса и сборку; **рабочий сайт не меняют**.
- При публикации GitHub Release собираются архивы интерфейса и Apps Script, manifest и SHA256SUMS.
- Выпуск Pages запускается отдельно для точного тега v<package.version>, с проверкой соответствия сервера.
- Ежедневно около 03:30 Asia/Irkutsk создаётся резервная копия метаданных. Google запускает временные триггеры с небольшим отклонением от указанного времени.
- В Настройках видно отсутствие свежей копии за 48 часов и код последней ошибки. Кнопка «Создать копию» запускает копирование вручную.

## Резервирование

Закрытая папка **Practicus_Metadata_Backups** принадлежит выделенному аккаунту и не должна иметь других редакторов/читателей. BACKUP_ROOT_ID записывается автоматически. По умолчанию сохраняются последние **7 успешных копий**; BACKUP_KEEP допускает 2–30.

Копируются Users, Groups, TeacherAccess, Assignments, Materials, Submissions, SubmissionFiles, Audit и Settings. В копии есть хеши паролей, оценки и приватные ссылки метаданных: её нельзя публиковать или передавать в GitHub/чат.

Открытые пароли, Script Properties, Google-токены, активные сессии, незавершённые загрузки, ограничения входов и очередь необработанного UserIntake не экспортируются. Бинарные файлы работ не дублируются. Копия не восстановит физически удалённую работу.

Сначала записывается pending-файл, затем он читается обратно, проверяется по SHA256 и только после этого становится успешной копией. Старые копии удаляются после успешной проверки новой. Зависшие pending-файлы старше двух суток убираются после следующего успешного копирования. Максимальный размер снимка — 20 МиБ; при превышении появляется ошибка, старые копии сохраняются.

Папка и копии должны оставаться доступными только владельцу. Копии в том же аккаунте защищают от ошибок БД, но не от полной потери самого Google-аккаунта. MFA и восстановление доступа необходимо сохранить. Для отдельной внешней резервной копии понадобится самостоятельная политика хранения; автоматически приложение её не создаёт.

## Подготовка восстановления

Восстановление — отдельная операция владельца, она **не заменяет рабочую базу автоматически**.

1. Убедитесь, что известен текущий DB_ID; сохраните его для отмены. Включите MAINTENANCE_MODE=true. Вход и операции приложения будут временно заблокированы. Сначала по возможности создайте свежую копию через редакторскую функцию runMetadataBackup.
2. В закрытой папке резервирования выберите успешный JSON-снимок. Скопируйте его ID из адреса файла в Script Property **RESTORE_BACKUP_ID**. Не используйте pending-файл.
3. Запустите **runPrepareRestore** в редакторе. Проверяются SHA256, формат, схема и принадлежность текущему хранилищу. Создаётся отдельная таблица Practicus_Restore; исходная не изменяется.
4. В Script Properties проверьте **RESTORE_STATUS=ready**, **RESTORED_DB_ID** и **RESTORE_REPORT**. При ошибке новая таблица не активируется. Неполная таблица остаётся помеченной INCOMPLETE и не должна использоваться.
5. Откройте подготовленную таблицу под владельцем. Проверьте группы, роли, блокировки, права, оценки и дату снимка: изменения после него могут быть потеряны. Отсутствующие файлы или известные удаления не восстанавливаются как доступные. Если текущую историю удалений прочитать нельзя, доступ ко всем восстановленным файлам закрывается до отдельной сверки. Оценки сохраняются.
6. Сессии, резервы загрузок и необработанный импорт в новой таблице пустые. Когда результат проверен, вручную замените DB_ID на RESTORED_DB_ID и выключите MAINTENANCE_MODE. Пользователям потребуется войти заново. DRIVE_ROOT_ID и AUTH_SECRET оставьте прежними.
7. При проблеме снова включите MAINTENANCE_MODE, верните сохранённый DB_ID и выключите режим обслуживания. Пока восстановленная таблица не активирована, откатывать рабочую базу не требуется.

Код восстановления проверен на моделях БД/Drive. Реальное восстановление вашей Google-таблицы автоматически не выполнялось и без вашего запуска не произойдёт.

## Откат версии приложения

Используйте архивы одного предыдущего GitHub Release. Сначала установите его четыре файла Apps Script и опубликуйте New version, затем выпустите соответствующий тег интерфейса. Для версий с release fingerprint workflow проверит пару. Возврат интерфейса без соответствующего сервера может нарушить совместимость.

Выпуски до 1.0.0 не имеют этого протокола и ежедневного резервирования. Для аварийного возврата к ним используйте сохранённую версию Web App и ранее сохранённую сборку Pages вручную. Откат кода не восстанавливает удалённые файлы и не меняет данные БД сам по себе.

## Регулярное обслуживание

Проверяйте время последнего backup в Настройках, свободное место Drive и ошибки Triggers/Executions Apps Script. Письма об ошибках триггеров приходят на Google-аккаунт владельца согласно настройкам Google. При отсутствии свежих копий исправьте причину, запустите runMetadataBackup и убедитесь в успешном результате.
