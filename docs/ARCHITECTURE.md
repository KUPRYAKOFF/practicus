# Архитектура и данные

## Размещение в одном аккаунте

```text
Браузер: GitHub Pages
  ├─ HTML/CSS/JS интерфейса, токен сессии только в памяти
  └─ невидимый Apps Script HTML Service bridge
       ├─ postMessage: origin + случайный channel + проверенный WindowProxy
       └─ google.script.run
            └─ Apps Script выделенного аккаунта
                 ├─ Google Sheets того же выделенного аккаунта: профили, хеши, задания, аудит
                 └─ Drive REST API с серверным токеном Apps Script того же аккаунта: закрытые файлы
```

Apps Script, таблица и файлы принадлежат одному специально созданному аккаунту приложения. Личный Google-аккаунт пользователя не участвует. `runInitialSetup` через внутреннюю `setup_` автоматически создаёт книгу и закрытую корневую папку при отсутствии их ID в Script Properties. Повторный запуск использует существующие ресурсы. Хранилище проверяется на владение аккаунтом, развернувшим Web App, и отсутствие публичных разрешений.

Apps Script получает разрешение Drive у владельца при установке и использует `ScriptApp.getOAuthToken()` исключительно на сервере. Не нужны отдельный OAuth-клиент, client secret или сохранённый refresh token. Drive REST API активируется через сервис Google Drive API v3 в проекте Apps Script. Google-токен не передаётся клиенту, не попадает в метаданные, URL или журналы приложения.

## Почему служебный iframe

Статическая страница GitHub Pages не имеет `google.script.run`. Web App Apps Script не предоставляет обычный управляемый CORS-интерфейс для произвольных preflight/заголовков. `fetch(..., mode: 'no-cors')` не позволяет прочитать ответ и здесь не используется. JSONP раскрыл бы токены в URL и не используется.

Служебный bridge живёт в HTML Service Apps Script, вызывает `google.script.run`, получает настоящие `File` через structured clone и передаёт HTML-форму с отдельным input на каждый файл. Это техническая служебная страница; весь пользовательский интерфейс находится на Pages.

Bridge разрешает сообщения только от `window.top` с точным `PAGES_ORIGIN` и каналом. Страница генерирует случайный 256-битный канал, принимает handshake только с Google-hosted origin с тем же каналом, затем привязывает все ответы к конкретному `event.source` и origin. Это учитывает вложенный sandbox iframe HTML Service. Токен сессии не попадает в URL. CSP страницы запрещает сторонний JS. В реальной среде нужно проверить вложенность iframe, ограничения third-party cookies и поведение Chrome/Firefox. До такой проверки bridge не считается подтверждённым транспортом.

## Передача файлов

1. Серверный `beginUpload` проверяет пользователя, аудиторию, статус, сроки, manifest, квоту и другие резервы под `LockService`.
2. Создаётся резерв с серверным временем начала, TTL 120 секунд и ключом идемпотентности. Он фиксирует поколение и предыдущую версию.
3. Форма передаёт Blob в Apps Script. Сервер заново проверяет фактический размер и сигнатуры всех файлов.
4. До каждого внешнего I/O сохраняется строка будущего файла и логический file ID. Drive получает этот ID в `appProperties`, что позволяет найти сироту при потере ответа.
5. Файлы создаются через Drive resumable upload от имени выделенного аккаунта приложения. URL сессии остаётся на сервере. Это не означает потоковую передачу через Apps Script: HTML Service всё ещё принимает комплект в память. Максимальный объём необходимо измерить.
6. Под короткой блокировкой сервер снова проверяет сессию, текущие права, квоту, срок резерва, состояние и базовое поколение. Затем готовит строки файлов и переключает указатель поколения сдачи. Новая дата и оценка меняются вместе с этой записью.
7. Старое поколение сразу недоступно пользователям. Физические старые/неудачные объекты удаляет очередь очистки; для неё сохранены Drive ID и логические ID.
8. При потере финального ответа `uploadStatus` восстанавливает результат по актуальному поколению. Повторный ключ не создаёт новую сдачу. При ошибке до commit прежняя сдача сохраняется.

Скачивание идёт авторизованными диапазонами до 256 КиБ. Каждый диапазон требует актуальной сессии и прав на файл. Base64 используется только для малого диапазона, не для всего файла в одном RPC. Браузер собирает Blob и инициирует скачивание. Процент отражает полученные байты. Загрузка не показывает фиктивный процент — только стадии.

## Авторизация

PBKDF2-HMAC-SHA256 из `@noble/hashes` 2.0.1, 600 000 итераций, 32 байта результата, соль для каждого пароля. Локальный тест сверяет результат с независимым Node crypto, включая Unicode. Реальное время KDF на Apps Script необходимо измерить при нагрузке.

Временный пароль показывается администратору один раз; в Sheets нет открытых паролей. После первого входа другие операции запрещены до смены. Смена/сброс отзывает сессии. Токен 256-битный, выводится HMAC-SHA256 с серверным случайным секретом и уникальными nonce; сервер хранит только SHA256 токена. Каждый запрос проверяет срок 8 часов, блокировку и отзыв. `last_seen` не используется для продления.

Попытки входа резервируются в постоянном листе: до 8 на нормализованный логин за окно 15 минут, глобальный ограничитель 120 попыток за 15 минут. Неизвестный логин получает такую же KDF-проверку. Apps Script не даёт надёжного клиентского IP; у первой версии нет внешней WAF/CAPTCHA, публичный endpoint всё ещё подвержен исчерпанию квот и DoS.

Публичные функции GAS: `api`, `uploadForm`, `doGet`, `runInitialSetup`, `runMetadataBackup` и `runPrepareRestore`. Все действия с данными проходят авторизацию Core. Видимый редакторский запуск владельца проверяет совпадение непустых `Session.getActiveUser().getEmail()` и `Session.getEffectiveUser().getEmail()` до обращения к Core: анонимный клиент и другой Google-пользователь Web App, выполняемого от имени владельца, получают отказ. Для чтения email манифест содержит userinfo.email. Внутренняя setup_ и триггер housekeeping_ заканчиваются `_` и недоступны через google.script.run. При ручном запуске используйте runInitialSetup: редактор также скрывает имена с подчёркиванием в конце.

## Sheets

Листы создаются при запуске `runInitialSetup` из редактора. Точная схема находится в `server/repository.js`; заголовки проверяются при чтении. Связи только по ID. Типизированные значения хранятся как JSON в ячейках: это сохраняет массивы/числа/null и предотвращает интерпретацию пользовательского текста как формулы. Обычные значения вручную допускаются только во входном листе `UserIntake`; команда импорта канонизирует их перед обработкой.

| Лист | Содержимое |
|---|---|
| Users | UUID, профиль, роль, группа, статус, квота, PBKDF2-хеш, соль, итерации |
| UserIntake | Ручной ввод ФИО, логина, роли, группы/подгруппы, состояние/ошибка импорта |
| Groups | Группы и активность |
| TeacherAccess | Отдельные разрешения на группу/подгруппу |
| Assignments | Название, тексты, массив targets, сроки, публикация, version, указатель поколения материалов |
| Materials | Файлы материалов, их поколение, владелец, Drive ID, размер, дата, очередь удаления |
| Submissions | Одна актуальная сдача на задание/студента, generation, attempts, оценка/решение, снимок группы |
| SubmissionFiles | Файлы поколений сдачи; актуальность определяется указателем Submissions.generation |
| Sessions | Хеш токена, пользователь, выдача/окончание/отзыв |
| LoginAttempts | Постоянные счётчики входа |
| UploadReservations | Резервы квоты, manifest, состояния, ключи повторов и результат |
| Audit | Событие, actor, объект, UTC-время, минимальные детали; без токенов и паролей |
| Settings | Зарезервированные несекретные настройки; в v0.1 основные параметры — Script Properties |

Отдельные `AssignmentTargets` из исходного ТЗ в v0.1 представлены типизированным массивом в строке Assignments, а не отдельным листом. Режимы и индексы можно изменить без изменения внешнего API. Sheets не даёт ACID-транзакций: блокировка не заменяет журнал операции и восстановление после частичного сбоя. Записи нового поколения подготавливаются до переключения указателя.

## Drive

Первая версия использует одну закрытую корневую папку и имена `file_<UUID>__<нормализованное имя>` без ФИО. Многоуровневое дерево папок не используется; права и группировка задаются метаданными, а не путями. Это уменьшает число внешних операций при 30 одновременных пользователях. Если будут нужны папки, модель прав менять не требуется.

Квота приложения учитывает актуальные логически доступные файлы, а не старые поколения и staging. AdminData отдельно показывает физические объекты и очередь. Фактическое место аккаунта проверяется через Drive About и может включать другие сервисы Google. До физического удаления и при параллельной замене требуется запас места сверх суммы пользовательских квот.

## Хранение и восстановление

Календарные два года отсчитываются по `createdTime` Drive, отдельно для каждого файла. Очистка не меняет grade и запись сдачи. Сначала файл логически закрывается и помечается, затем выполняется DELETE Drive. Ошибка остаётся видимой для повтора. Возвращаемый 404 считается уже завершённым удалением.

При восстановлении метаданных проверяйте поколения и физическое наличие файлов. Не редактируйте нормализованные рабочие листы вручную. Книга БД, копии и Script Properties доступны только доверенным администраторам.

## Резервирование и выпуск 1.0.0

server/backups.js формирует снимок 9 таблиц с контрольной суммой SHA256 и схемой. Серверные токены/Script Properties, сессии, LoginAttempts, UploadReservations и необработанный UserIntake исключаются. BackupStore сохраняет pending-файл в отдельной папке только владельца, читает его обратно и переименовывает после проверки. Ротация удаляет старые копии только после фиксации новой. Lease в Script Properties защищает от двух одновременных backup.

Подготовка восстановления требует MAINTENANCE_MODE=true и создаёт новую книгу. Сопоставляются текущие отметки удаления и наличие файлов. Если историю удаления нельзя прочитать, доступ к восстановленным файлам закрывается. Сессии в новой таблице пустые, оценки сохраняются, DB_ID автоматически не меняется.

Выпуск проверяет публичный ответ /exec?health=1: application, version и backend_build. SHA256-отпечаток вычисляется из серверных исходников, манифеста, Main.gs, Bridge.html и версии package.json, без конфигурации и токенов. Он встраивается в Core.gs и release manifest. Совпадение проверяется перед публикацией Pages для точного тега. Push в main не публикует рабочий сайт. Это проверка соответствия кода, а не файловый или нагрузочный тест.
